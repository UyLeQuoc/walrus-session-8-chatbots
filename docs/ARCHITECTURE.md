# Architecture

Everything below is verified against the MemWal source in `memwal/` (SDK 0.1.8 in repo, 0.1.7 on npm) unless marked **[unverified]**.

## 1. Components

One core, many channels. Every channel adapter turns an inbound message into `handleTurn({ personId, channel, text })` and streams the reply back. Nothing channel-specific touches memory.

```
 Web chat (Vite SPA)   Telegram (grammY)   Discord (discord.js)   Slack (Bolt, socket mode)
        │                     │                    │                      │
        └──────────── channel adapters (apps/server/src/channels/*) ──────┘
                                        │
                              ┌─────────▼─────────┐
                              │ packages/core     │  agent loop: recall → LLM (OpenRouter) → tools
                              │ packages/memory   │  MemWal client factory, write/recall policy, dedupe
                              └───┬───────────┬───┘
                                  │           │
                    ┌─────────────▼──┐   ┌────▼──────────────────────────┐
                    │ Postgres (Neon)│   │ Walrus Memory relayer          │
                    │ people,        │   │ /api/*  /sponsor  /v1/owners/* │
                    │ identities,    │   └────┬──────────────────────────┘
                    │ delegate keys, │        │
                    │ connect tokens │   Sui mainnet (MemWalAccount, delegate keys)
                    └────────────────┘   Walrus mainnet (SEAL-encrypted blobs)
```

Monorepo (pnpm workspaces + turborepo):

| Path | Purpose |
|---|---|
| `apps/web` | Vite + React + Tailwind v4 + shadcn/ui. Chat UI (`useChat` streaming), `/connect/:token`, `/disconnect/:token`, `/me` memory viewer, wallet sign-in. Static build, deployed to Vercel or Cloudflare Pages. |
| `apps/server` | Hono HTTP API (`/api/chat` streaming, `/api/connect/*`, `/api/me/*`) **and** the long-running channel adapters (Discord gateway, Telegram long polling, Slack socket mode) in one Node process. Deployed to Railway. |
| `packages/core` | Agent loop, system prompt, tools (`remember`, `recall`), streaming helpers. Channel-agnostic. |
| `packages/memory` | MemWal client factory (guest vs owned), memory text format, dedupe, recall policy, provenance, `signedRequest` for endpoints the SDK does not wrap. |
| `packages/db` | Drizzle schema + client: `people`, `channel_identities`, `delegate_keys`, `connect_tokens`, `turn_log`. |
| `memwal/` | Read-only reference clone of MystenLabs/MemWal. Gitignored. |

### Identity across channels

A `person` is the unit of memory. Channel identities (`telegram:123`, `discord:456`, `slack:T1/U1`, `wallet:0xabc`) map to one person. Linking happens through the same `/connect` flow: the link carries the channel identity, the user signs with their wallet, and the server merges that identity into the person owning that wallet. That is how the same memory follows a user from Telegram to web to Discord.

Web sign-in: wallet challenge (`signPersonalMessage` over a server nonce) → session cookie → `person`. No passwords, no OAuth.

## 2. Identity model

Two modes per person, stored in `people.mode`:

| | Guest | Owned |
|---|---|---|
| MemWalAccount | Operator's (`MEMWAL_ACCOUNT_ID`) | The user's own (`users.account_id`) |
| Delegate key used by bot | Operator's (`MEMWAL_PRIVATE_KEY`) | Per-user key generated by the bot, registered on the user's account, stored encrypted in `users.delegate_key_enc` |
| Namespace | `hippo-guest:<personId>` | `hippo` (inside the user's own account, so no user id needed) |
| Who can revoke | Nobody but the operator | The user, on-chain |
| Write rate limit | Shared 30/min per delegate key across all guests | 30/min per user |

Team/shared scope is a stretch goal (Discord guild or Slack workspace namespace `hippo-team:<id>` in the operator account). Personal scope ships first.

Namespace names are public on-chain metadata. Person IDs are random UUIDs, not channel IDs,, but nothing else goes into a namespace.

Why the bot generates the key instead of asking users to paste one from the dashboard: pasting a private key into Discord is what the official example chatbot does, and it is the wrong lesson to teach. Generating server-side and registering the public key on-chain is exactly what the MCP plugin does.

## 3. Onboarding flow (owned mode)

Mirrors `apps/app/src/pages/ConnectMcp.tsx` and `SetupWizard.tsx`, minus the localhost bridge.

```
User            Bot (apps/bot)                 Web (apps/web)                    Relayer / Sui
 │ /connect         │                               │                                │
 ├─────────────────▶│ generateDelegateKey()         │                                │
 │                  │ store {pub, priv_enc, state}  │                                │
 │                  │ token = random 32B            │                                │
 │◀── link ─────────┤ https://hippo.app/connect/<token>                              │
 │ open link                                        │                                │
 ├─────────────────────────────────────────────────▶│ GET /api/connect/<token>       │
 │                                                  │  → {publicKey, label}          │
 │ connect wallet (Slush / zkLogin)                 │                                │
 │                                                  │ fetchAccountIdForOwner()  ─────▶ Sui registry dynamic field
 │                                                  │ if none: create_account   ─────▶ POST /sponsor → sign → /sponsor/execute
 │                                                  │ add_delegate_key(pub,label)────▶ POST /sponsor → sign → /sponsor/execute
 │                                                  │ POST /api/connect/<token>/done │
 │                                                  │   {accountId, wallet, digest}  │
 │◀── "connected, migrating N guest memories" ──────┤                                │
```

Details that matter:

- **Sponsorship allowlist** (`services/server/src/routes/sponsor.rs`): a sponsored tx may contain exactly one of `account::create_account`, `account::add_delegate_key`, `account::remove_delegate_key` (batched removals allowed). Nothing else. So two transactions for a new wallet, one for an existing account. The user never needs SUI.
- `/sponsor` needs `authTimestamp`, UUID `authNonce`, and `authSignature` = personal-message signature over sender + tx-kind hash. `createSponsorAuthorization()` is exported from `@mysten-incubation/memwal` and does this. Copy `useSponsoredTransaction.ts` wholesale.
- Account lookup: `fetchAccountIdForOwner(suiClient, registryId, owner)` reads the registry's `accounts` Table dynamic field keyed by address (`apps/app/src/utils/suiClientCompat.ts`). One account per address, enforced on-chain.
- Each account holds max 20 delegate keys. Label the bot's key `hippo (<channel>:<username>)` so it is recognizable in the dashboard.
- The connect token is single-use, expires in 10 minutes, and binds `{personId, channelIdentity, publicKey}`. The done callback is verified server-side: fetch the `MemWalAccount` object and confirm `delegate_keys` contains our public key before flipping the user to owned mode. Never trust the browser's payload alone.
- After connect, migrate guest memories: recall the guest namespace in pages (broad queries) and `rememberBulk` into the user's account. Note the limitation in §7.

**[unverified]** CORS on `relayer.memory.walrus.xyz/sponsor` for a non-Walrus origin. The dashboard calls it from `memory.walrus.xyz`. First spike: call `/sponsor` from `localhost:3000`. If blocked, proxy through `apps/server` (the request is already signed by the wallet, so a proxy adds no trust).

**[unverified]** Whether the managed mainnet relayer accepts `/sponsor` for arbitrary accounts without a dashboard session. The code path has no such check, but usage limits exist.

## 4. Revoke flow (the demo)

`/disconnect` → link to `/disconnect/<token>` → wallet signs sponsored `remove_delegate_key(pub)`. The contract bumps the account's rotation counter, so the bot's cached SEAL key is useless for new memories and the relayer rejects the delegate on every request. Bot flips the user back to guest mode and says so. `/connect` again registers a fresh key.

For the article, capture: recall works → revoke tx digest → same question, bot has nothing → re-grant → recall works. Also show the dashboard's delegate list before and after.

## 5. Memory layer (`packages/memory`)

### Text format

MemWal stores plain text, so metadata lives inside the text in a fixed, parseable prefix:

```
[profile] [by:@uy] [2026-09-25] Prefers pnpm and TypeScript strict mode. Works on Sui + Next.js.
[gotcha] [by:@minh] [#backend] [2026-09-26] Vercel AI SDK v6 middleware needs specificationVersion "v3" or wrapLanguageModel throws.
```

Prefix grammar: `[type]` then any number of `[key:value]` tags, then a date, then the fact. Keep the fact in the user's own words. Relative dates are converted to absolute before writing.

### Write policy

The model has two tools:

- `remember({ type, text, scope })` — `scope` is `personal` or `team`. The tool converts relative dates, prepends tags, runs the dedupe check, then `rememberAndWait` (personal) or `remember` (team, fire and forget).
- `recall({ query, scope, limit })` — explicit recall for when the model decides it needs more.

System prompt follows the official four-part template (`memwal/docs/guides/system-prompt-templates.md`, "Team knowledge base" variant): recall first, write proactively in the same turn, skip one-off chatter, namespace rules. Expected writes: 3 to 8 per session.

`withMemWal` middleware is **not** used. Its `autoSave` runs `analyze()` on every user message, which produces low-quality duplicate facts and is exactly the "decorative memory" the judges warn about. We keep control of what is written.

### Dedupe

`remember()` is append-only (no upsert, no idempotency on text). Before every write: `recall({ query: text, limit: 3, maxDistance: 0.25 })`. If a hit exists, skip and tell the model it already knew this. Distance bands from `SKILL.md`: `< 0.25` duplicate, `0.25–0.55` related, `0.55–0.7` weak, `>= 0.7` unrelated.

### Recall policy

Per turn, before generation:

1. Session start (first message in 6 h): recall `profile` and open `commitment` entries with fixed queries, limit 8.
2. Every turn: recall with the user message as query, `limit 6`, `maxDistance 0.6`, in the personal scope. In guild channels also recall the team scope, limit 4.
3. Inject as untrusted data using the SDK's `formatUntrustedMemories()` (nonce-delimited, JSON-encoded) plus its system instruction. Reuse, do not reinvent.
4. Keep the list of injected memories for the turn so the reply can cite `blob_id` when asked "how do you know that?".

Indexing lag is a few seconds; the tools use `rememberAndWait` for personal facts so a follow-up question in the same minute can find them.

### Provenance

Team memories carry `[by:@user] [#channel]`. Personal memories carry `[by:@user]` only. The reply template for team recall is "According to @minh in #backend on Sep 26: …".

## 6. Slash commands

| Command | Behaviour |
|---|---|
| `/connect` | Start owned-mode onboarding (link). Same command on every channel; on web it is a button. |
| `/disconnect` | Revoke link. |
| `/whoami` | Mode, account object ID with Suiscan link, delegate label, memory count via `POST /api/stats`. |
| `/memory` | Last N memories (recall with broad query per type), each with blob ID. |
| `/memory search <q>` | Explicit recall with distances shown. |
| `/memory forget` | `POST /api/forget` on the namespace (index only, blobs persist). Explain that in the reply. |
| `/memory off` / `on` | Per-user toggle used for the baseline phase. Logged for the article. |
| `/proof` | Blob IDs used in the last answer, with Walrus aggregator links. |

## 7. Known limitations and how we present them

- **No "read memory text by ID"** in the relayer or SDK. `GET /v1/owners/:owner/memories` returns metadata only (blob ID, size, timestamps), never text. Listing means recall with broad queries. Migration guest → owned therefore recalls in rounds by type and may miss entries. File as a feature request.
- **Forget is index-only.** Blobs live until epoch expiry. Permanent delete is the Security Delete API signed by the owner wallet; out of scope, link to it.
- **Relayer sees plaintext** during embed and encrypt. Ownership is about access control and portability, not hiding data from Mysten's relayer.
- **Bot custody of delegate keys.** Encrypted with `KEY_ENCRYPTION_KEY` (32-byte, env), AES-256-GCM. A leaked DB alone does not leak keys. Users can revoke on-chain at any time.
- **Rate limits.** Write path 30/min per delegate key. Guest mode shares one key. Owned mode isolates users. This is a real argument for the architecture; measure it.

## 9. Portability demo (Claude Code)

The MCP plugin reads `~/.memwal/credentials.json`:

```json
{
  "delegatePrivateKey": "<64 hex>",
  "delegatePublicKeyHex": "<64 hex>",
  "delegateAddress": "0x…",
  "walletAddress": "0x…",
  "accountId": "0x…",
  "packageId": "0xcee7…",
  "relayerUrl": "https://relayer.memory.walrus.xyz",
  "label": "Claude Code"
}
```

Two ways to show the same memory in Claude Code: (a) the user runs the normal `memwal_login` in Claude Code against the same wallet, which adds a second delegate key to the same account, then `memwal_recall --namespace hippo`; (b) export from hippo's web page. Use (a): it is the honest, zero-custom-code path and shows two independent delegates on one account.
