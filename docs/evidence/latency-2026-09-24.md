# What memory costs a turn, and the before/after it buys

Measured 2026-09-24 on the mainnet relayer with `google/gemini-2.5-flash`.

## The before/after, now measured

`pnpm demo` asks the same session-two questions a second time with memory off,
on the same model, and fails if a memory-off answer knows something no model
could guess (port 5433, that the person works on Sui and Next.js) or answers in
Vietnamese unasked. Package manager and ORM are shown but not scored, since a
generic answer may list pnpm, bun or Drizzle by chance.

```
BASELINE — the same questions, memory off
        Which package manager should I use here?
        off: Which language or ecosystem are you working with?
        on:  Bạn nên dùng bun.
        Which ORM did we settle on?
        off: We did not settle on an ORM.
        on:  Chúng ta đã quyết định sử dụng Drizzle làm ORM cho dự án này.
  PASS  What port is the database on?
        off: Which database?
        on:  Postgres của chúng tôi chạy trên cổng 5433.
  PASS  What do you know about me?
        off: You are @mai, and you're interested in what I know about you.
        on:  Bạn là Mai. Bạn làm việc với Sui và Next.js, …
```

The memory-off control passed in all three runs that included it.

## What it cost

A recall takes about a second on this relayer, and varies: a single one was
measured anywhere from 1.0 to 2.2 seconds. Before this change a session's first
turn ran five of them before the model could start — the message, three
natural-language pulls for profile, style and commitments, and the corrections
pull — and every later turn ran two.

```
COST — median over 4 questions (first run, before any change)
  whole turn, memory on (first of a session):  7.1s
  whole turn, memory off:                      1.1s
  recall alone, first turn of a session:       5.2s
  recall alone, later turns:                   2.0s
```

## What did not help: running them in parallel

The recalls ran one after another on the belief that concurrency made the
relayer drop matches. `docs/SPIKES.md` §H had already disproved that, so they
were issued together, bounded by the per-key limiter. Two eval runs: recall at
a session's first turn 5.3s and 5.1s, against 5.2s before. A direct probe of
four recalls gave 5.93s in a row and 3.97s in parallel, but the eval saw no
gain: the relayer appears to answer one key's recalls roughly in turn. With
nothing measurable gained and more instantaneous load on a key every guest
shares, they were put back in sequence.

## What did: asking fewer questions

**Corrections.** Most people have never corrected anything, and the server knows
from `memory_index`. For them the corrections recall is skipped: later turns
went from 2.0–2.2s of recall to 1.0–1.1s across three runs.

**Session start.** Every memory's text begins with its type tag, so the tags are
the query. On two namespaces, one recall for `[profile] [style] [commitment]`
returned every profile, style and commitment memory that the three separate
pulls returned between them (3/3 and 5/5), where a one-sentence natural-language
query missed the style memory on one of them.

Four samples per run were too few to see it: two eval runs gave 3.1s and 5.1s.
So `pnpm --filter @hippo/core bench:recall` alternates old and new, ten rounds
each, on the same namespace:

```
10 rounds, alternating, namespace hippo-guest:demo-mufnpy6s
  old, message + 3 pulls: median 3.76s, slowest 15.37s
  new, message + 1 pull:  median 1.97s, slowest 3.36s
```

About 1.8 seconds off the median first reply, and the slow tail mostly gone:
fewer calls, fewer chances to hit a dropped recall and its retry.

Both eval runs with the merged pull passed everything, with all four session-two
answers in Vietnamese, the style memory having survived the change.

## Still true

A session's first memory-on turn is several seconds slower than a memory-off
one. That is the relayer's per-recall latency, not something the client can
remove, and it is the number to watch if the relayer changes.
