# Export: the memory as a file the person keeps

Measured 2026-09-24 on a local server against the mainnet relayer and
`google/gemini-2.5-flash`, with every bot token blanked so the local process
could not compete with production's Telegram polling.

## What the file holds, and how its text is checked

There is no read-by-blob-id in Walrus Memory (checked again in SDK 0.1.8), so
text comes back only through recall, capped at 100 results a call. The export
recalls on each type tag, `[profile]` to `[style]`, stopping as soon as every
stored blob is found. Each recovered line is hashed and compared with the
`text_sha256` hippo recorded in `memory_index` when it wrote the memory: the
file can say not just "this came back" but "this is exactly what was written".

Nothing is stored. The file is built per request, served `Cache-Control:
no-store`, and memory text never reaches Postgres.

## End to end

A fresh person taught four facts on the web, started a team and added a fact to
it, then linked a CLI session to the same memory. After 75 seconds:

```
web /export → files: 0
  4 memories. Text recovered for 4 of them, and 4 match the fingerprint I
  recorded when I wrote them. Download it from the Export button on …/me.

GET /api/me/export?format=json → 200 application/json; charset=utf-8
  | attachment; filename="hippo-memory-2026-09-24.json" | cache no-store
coverage: {"memories":4,"withText":4,"verified":4,"stillWriting":0,"neverLanded":0}
  verified  [style] Answer briefly.
  verified  [gotcha] Our Redis runs on port 6380 because 6379 is used by the legacy queue.
  verified  [decision] We deploy everything on Fly.io, never Heroku.
  verified  [profile] I'm Linh. I run the platform team at a logistics startup in Da Nang.

GET ?format=md → 200, 1832 chars

cli /export → files: hippo-memory-2026-09-24.md (1832 chars),
                     hippo-memory-2026-09-24.json (4846 chars)
```

## In a real browser

The Export button on `/me`, clicked in Chrome against the same person, showed
"4 memories, text for 4, verified for 4". The save itself was intercepted in
the page, so no file was written to the machine.

It also found a defect no test could: across origins the browser hides
`Content-Disposition` unless the server exposes it, so every download was saved
as the fallback `hippo-memory.json`. The server now sends
`Access-Control-Expose-Headers: content-disposition`, and the next download was
named `hippo-memory-2026-09-24.md`. Production runs same-origin behind Vercel
and never hit this; the Walrus Site would have.

## What it found about team memory

The team fact is not in the export, and not because of the export.
`/team remember` writes through a port with no `onWrite`, so a team memory is
never recorded in `memory_index`: there is no per-person list of what someone
gave a team, and a team write that fails on Walrus is never noticed — the person
has already been told "Added". The export says plainly that team contributions
are not in the file. Tracking team writes is part of `docs/GOAL.md` M8 task 3,
because it changes `pnpm evidence`, `/memory forget` and `/me` together.

## Limits, as the file states them

- Text is recovered through recall; coverage is reported, never assumed.
- The ciphertext cannot be decrypted without the relayer today
  (`docs/issues/12`).
- Storage expires; expiry is listed where the relayer reports it, for the
  primary account only.
- In guest mode the memory is in hippo's account, not the person's.
