# Decisions log

- 2026-09-23 — Railway app sleeping stays off. Three reasons, and the first is fatal on its own. Telegram is long polling, which is an outbound loop from our own process, so a sleeping service is not polling and the bot simply never hears anything; Railway wakes a service on an inbound request and a Telegram message is not one. Second, it would probably cost more: the conversation buffer is an in-memory Map, sleeping wipes it, and the next message then counts as a session start, which fires four recall queries instead of one and injects up to ten memories into the prompt. Third, memory writes settle in the background about 24 seconds after the reply, which is exactly when a service would be idle enough to sleep, and the user has already been told it saved. Railway is about $2.03 a month estimated, roughly a dollar more before the deadline, so there is nothing here worth the risk. If it ever becomes worth it, the order is: right-size the container first, because Railway bills resource-seconds and that changes no behaviour; move Telegram to webhooks only after that.
- 2026-09-23 — The connect and disconnect pages are covered by a jsdom test with a stand-in wallet, not by registering a real wallet-standard wallet and not by driving a browser against production. Registering a wallet would additionally exercise dapp-kit's discovery, which is not our code, and a production run would mean putting a real private key in a page. What had never executed anywhere was the page's own orchestration: create then add then confirm, the 409 retry while the node catches up, the user-paid fallback, and the refusal to ask a wallet to sign when it cannot pay the gas. Those five now run on every commit. The mainnet half is already proven by `scripts/spike-revoke.ts`, so between them the flow is covered end to end without a spare wallet.
- 2026-09-22 — Use `ai` v7 across the repo instead of v6. `@openrouter/ai-sdk-provider` 3.x requires v7 and we do not use `withMemWal`, so nothing pins us to v6.
- 2026-09-22 — Web app is a Vite SPA, so all bots and the API live in one Hono process (`apps/server`). Long-lived gateways need a persistent process anyway.
- 2026-09-22 — CORS default allows `localhost:5173` and `5174`; the developer's machine has another app on 5173.
- 2026-09-21 — Memory writes no longer block the reply. `rememberAndWait` measured 23.7 s on mainnet; the tool now accepts the job and records the blob ID in the background (`policy.ts`, `port.ts`).
- 2026-09-21 — The package ID is read from the relayer's `GET /config` at runtime, not from the docs. The live mainnet package is an upgrade the docs do not mention, and the sponsorship allowlist compares against it.
- 2026-09-21 — Every relayer call is paced by a per-delegate-key limiter with `retry_after` handling. The observed limit is 60 weighted requests per minute, shared by all guest users on one key.
- 2026-09-21 — Default recall `maxDistance` is 0.75, not 0.6. Measured distances for clearly relevant matches ran to 0.745 once the metadata prefix was embedded with the fact.
- 2026-09-21 — Keep the `[type] [by:@user] [date]` prefix on stored memories. A/B on mainnet showed it costs 0.006 mean distance and no ranking, while buying type filtering, provenance and dates.
- 2026-09-21 — `DEFAULT_MAX_DISTANCE` is 0.8. Measured true positives reached 0.777; a 0.6 cutoff, which is what `withMemWal`'s default `minRelevance` works out to, would have dropped half of them.
- 2026-09-21 — Only the object form of `recall()` is used. The positional overload dropped every match in testing.
- 2026-09-22 — On `/disconnect`, hippo deletes its own encrypted copy of the delegate private key, not just its `revoked` flag. Revocation on chain is now measured to work, but it takes up to about half a minute (`docs/evidence/revocation-2026-09-22.md`); destroying the credential closes that window on hippo's side immediately, and costs nothing to keep.
- 2026-09-22 — `MEMWAL_REGISTRY_ID` and `MEMWAL_ACCOUNT_ID` must name the deployment that `GET /config` reports, never the documented one. Two Walrus Memory packages are live on mainnet with separate registries, and mixing them produced both an opaque sponsorship failure and a wrong-but-plausible account (`docs/issues/11`). `pnpm diagnose` now fails when the chain and the relayer disagree, so this cannot go unnoticed again.
- 2026-09-22 — Account setup falls back to a user-paid transaction when the relayer will not sponsor it. Sponsorship is preferred and is what makes onboarding one click, but owning your memory is the centre of this project and cannot rest on an endpoint we do not control. The connect page says who is paying before the user signs.
- 2026-09-22 — Keep the metadata prefix and the relayer-mediated read path; client-side SEAL decryption for `/proof` is shelved. The earlier reason was wrong: `seal_approve` refused our delegate because we were evaluating it against an account in the superseded deployment, not because the key was unregistered. It is now worth retrying, but it is optional work and `/proof` already links the public ciphertext, which shows the memory is a real Walrus blob.
- 2026-09-22 — Recalls are issued one at a time, not with `Promise.all`. Measured: nine dropped recalls in one eval run with concurrent queries, zero across two runs with sequential ones. Latency is the right thing to trade for a bot that does not randomly forget.
- 2026-09-22 — The connect callback derives the user's wallet from the on-chain account owner and ignores any wallet in the request body. Trusting the body allowed an attacker who completed the flow honestly to merge a victim's person into their own session. See `docs/evidence/security-review-2026-09-21.md`.
- 2026-09-22 — Relayer metadata calls are signed with the same credential as the memory port. Signing with the operator key while naming a user's account silently redirected `/memory forget` to the operator's namespace, so the bot claimed to have forgotten things it had not.
- 2026-09-22 — `/link` refuses a redemption when the redeeming conversation already holds memories. Merging always costs the redeemer their person, so a code sent by a stranger was a one-message takeover. Linking a fresh channel, which is the only real use case, is unaffected.
- 2026-09-22 — Never leave a polling loop running against the relayer. One left over from a test spent hours issuing a recall every five seconds on the shared delegate key, which both wasted the 60/min budget and muddied a measurement. Wait on a condition with a bounded loop, and kill it when the check is done.
- 2026-09-22 — Corrected: sequential recalls do not fix the dropped-recall bug. A clean re-run with no background load produced 15 drops, the worst of four runs. Sequential recalls and concurrency 2 are kept for load reasons only. The retry is what keeps the bot from forgetting. The wrong hypothesis is left in `docs/SPIKES.md` §H on purpose.
- 2026-09-22 — Corrected: `/me` does not offer permanent deletion, because the relayer has no endpoint that deletes a current blob. The Security Delete API is legacy-migration cleanup and explicitly never accepts caller-supplied blobs; I read `securityDeleteEnabled: true` as a user capability and it is not. `/memory forget` now states the limit plainly instead of pointing at a path that does not exist. Filed as `docs/issues/09`.
- 2026-09-22 — `pnpm restore` ships even though restore does not currently work on this account, because it prints what we wrote beside what the relayer claims and warns on a mismatch. A recovery tool that shows the discrepancy is worth more than no tool, and it is the repro for `docs/issues/10`.
- 2026-09-22 — `readAccount` verifies the object's Move type before trusting anything on it. The connect callback reads the user's wallet from that object, and a wrong-type object with an `owner` field would otherwise be accepted. The delegate check already made it unexploitable; depending on a second check to rescue the first is not a design.
- 2026-09-22 — One `pnpm.overrides` entry forces esbuild to a patched version. `drizzle-kit` 0.31.11, the latest, still pulls `@esbuild-kit` with esbuild <=0.24 and its dev-server advisory. drizzle-kit only bundles a config file and never starts that server, so it was not exploitable, but `pnpm audit` now runs in CI and a clean audit is worth more than a comment explaining why a red one is fine.
- 2026-09-22 — Wallet sign-in on the web recovers the address from the signature and never accepts one from the request, and burns the nonce before doing anything else. The connect-callback takeover came from trusting a body field, so this path was built the other way round from the start.
- 2026-09-22 — A sign-in challenge has no `person_id`. It belongs to nobody until somebody signs it, so `connect_tokens.person_id` is nullable and `loadToken` filters challenges out, which also stops a challenge nonce being usable as a connect token.
- 2026-09-22 — `signedIn` on `/api/me` means the session resolved, not that a cookie was present. A signed-out session leaves its cookie behind, and reporting that as signed in showed the wrong thing.
- 2026-09-22 — Every assistant reply carries the memories it was built from, rendered under the answer with a link to each Walrus blob. Memory working and the model guessing read identically in plain text, and judging criterion one is precisely whether memory is doing real work, so it has to be visible in the moment rather than only through `/proof`.
- 2026-09-22 — The web pages have render tests in jsdom. They had never been opened in a browser, and a passing typecheck and build say nothing about a component that throws on first paint, which is exactly what a judge clicking the live URL would hit. The tests immediately found two real things: `/me` blanked with `Cannot read properties of undefined (reading 'filter')` when the memories endpoint returned an unexpected shape, and the chat page's rewritten empty state had never actually landed in the file.
- 2026-09-22 — The production image does not typecheck or test. It was doing both and the build failed, because the image installs no `vitest` and the package tsconfigs include their test files. CI already runs those on every push; a deploy failing for a reason a deploy cannot fix is worse than not checking there at all. Verified instead by building the image and running it: it boots, serves `/api/health`, and answers a real chat turn.
- 2026-09-22 — Added `.dockerignore`. Without it the build context carried `memwal/` (71 MB), every `node_modules` (463 MB) and `.env` to the daemon. Confirmed after the change that neither `.env` nor `memwal/` exists in the image.
- 2026-09-22 — The deploy does not run `drizzle-kit push`. It was in the Railway start command; push can drop a column to reach the target schema, and this database holds users' encrypted delegate keys and their memory index. Schema changes go out deliberately, with someone looking at the diff.
- 2026-09-22 — The web app proxies `/api/*` to Railway through `vercel.json` rather than calling it cross-origin. The session cookie is `SameSite=Lax`, which browsers do not send cross-site, so with the page on vercel.app and the API on railway.app every message arrived as a new person and the bot appeared to have amnesia. Proxying keeps them same-site, which also keeps `SameSite=Lax` as the CSRF defence the security review relied on; `SameSite=None` would have fixed the symptom and removed the protection.
- 2026-09-22 — The dedupe check before a write is best-effort. In production the relayer failed that recall with "temporarily cannot verify credentials (upstream unavailable)" and the error took the whole write down, so the bot told the user it could not remember anything. A duplicate memory is a much smaller problem than a lost one.
- 2026-09-22 — `/api/health/deep` probes the database and the relayer and names whichever is failing, while still returning 200 so Railway does not restart a container that is serving fine. During the real-use week a user saying "it is broken" needs a one-URL answer, and hippo depends on two services it does not control.
- 2026-09-22 — `pnpm prune:people` only removes a guest person with no memories, no turns, no delegate key and no wallet identity, older than an hour. Anonymous visitors legitimately create person rows, so a looser rule would delete someone mid-conversation. `pnpm evidence` already counts only people who have memories, so the headline submission number was never distorted.
- 2026-09-22 — A cross-origin page carries its identity in `x-hippo-guest` and `x-hippo-session` headers rather than a cookie. Walrus Sites cannot proxy, so a page there must call the API cross-origin, where a `SameSite=Lax` cookie is never sent. A header is never attached by the browser on its own, so unlike `SameSite=None` this cannot be used for CSRF; the cost is `localStorage` instead of `HttpOnly`, and same-origin deployments never take this path.
- 2026-09-22 — `sites-config.yaml` reuses WalForm's mainnet context, including its notes on why site-builder and the walrus subprocess need different RPC endpoints. Rediscovering that would have cost an afternoon.
